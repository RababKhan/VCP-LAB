# Experiment Design (Phase 4A)

Status: designed and piloted on 2026-10-27. The full matrix has **not** been run.

## 1. Verified dataset facts
Evidence: `results/phase4a/inspection/*.json`, frames in `results/phase4a/frames/`, JVET VTM per-sequence configs.

| Sequence | Resolution | fps | Bytes | Frames in file | Content frames | SHA256 |
|---|---|---|---|---|---|---|
| BasketballPass | 416x240 | 50 | 150,059,520 | 501 | 500 | de0dcc61…f593ed698 |
| BlowingBubbles | 416x240 | 50 | 150,059,520 | 501 | 500 | ffe4039f…02a3d77028e566a0f82313a54d180e2 |
| BQMall | 832x480 | 60 | 720,046,080 | 601 | 600 | 02490741…d0ef8d50016d236e7e98efdf5e3deb9a7cc60aa61c0d55c4e61b52 |
| BasketballDrive | 1920x1080 | 50 | 3,116,620,800 | 501 | 500 | 1c4cecebc10efb18471ddcb43aa2680c61c6525a8f53b84267a1a04f73eb6334 |

All four (confirmed from the data):
- 10-bit samples in 16-bit little-endian words (every high byte is 0..3), planar 4:2:0, 0 trailing bytes.
- The **last frame** of every file is an NTT DOCOMO copyright text card (temporal jump of 413-457 vs median 17-43; visually inspected). Experiments encode only the content frames (`-f 500` / `-f 600`).
- 100 % of samples have their two least-significant bits equal to 0.

Interpretation: the 10-bit files were made by left-shifting 8-bit sources by 2 bits. This matches the JVET per-sequence configs, which list `InputBitDepth: 8` for all four sequences. Effective precision is therefore 8 bits; encoding is still done in 10-bit (`main_10`).

## 2. Encoder behaviour confirmed from logs
- Default random-access GOP size 32, constant across all QPs and presets of a sequence.
- First intra picture is not POC 0: `IDR_W_RADL` at POC 15 for 50 fps (intra period 48, then CRA at 63, 111, …) and at POC 31 for 60 fps (intra period 64). Pictures before it are RADL leading pictures.
- Source explanation (code, not interpretation): since VVenC 1.10.0 `m_poc0idr` defaults to false (`vvencCfg.cpp:391`, changelog line 197), so the first GOP is aligned with the others. We keep this default.
- Slice QP is a **base QP**: hierarchical offsets give e.g. I-slice QP 28.5 and B-slice average 39.27 for `-q 32` (BasketballPass, medium).
- Thread count changes the bitstream (t4 vs t8: 26,972 vs 27,168 bytes, Y-PSNR 35.3109 vs 35.2919), because VVenC derives tiles/WPP/IFP from it (`--mtprofile auto`). Thread count is therefore fixed for all runs.
- Same configuration, same threads → bit-identical bitstreams (3/3 repeats).

## 3. Controlled design
| Group | Varied | Fixed |
|---|---|---|
| qp_sweep | QP ∈ {22, 27, 32, 37} | preset medium |
| preset_sweep | preset ∈ {faster, fast, medium, slow, slower} | QP 32 |

QP 32 + medium is run once and belongs to both groups → **8 unique configurations per sequence**, 32 in total.

Fixed for every run: VVenC 1.14.0 / VVdeC 3.2.1 (Windows MSVC build), `-c yuv420_10`, sequence fps, all content frames, `--qpa 0`, `-t 8` (encoder) and `-t 8` (decoder), `--refreshtype cra --refreshsec 1`, constant QP (no rate control), GOP = preset default (32), AC power, power plan recorded per run.

Machine-readable manifests: `configs/pilot_manifest.json`, `configs/full_manifest.json` (generated by `scripts/make_manifest.py`). Runner: `scripts/vvc_runner.py` (resumable, never overwrites).

## 4. Measurements and definitions
- **Encoding time**: wall-clock time of the `vvencapp` process (includes start-up and file reading), and encoder-reported `Total Time`. Both are stored.
- **Decoding time**: wall-clock of `vvdecapp` *without* output (pure decoding); the decode that writes the reconstruction is timed separately.
- **Bitrate** = bitstream bytes × 8 × fps / frames. Matches the encoder report within 0.0001 kbps in all 36 pilot runs.
- **PSNR** (primary; identical to the VVenC report in all 36 pilot runs, max difference 0.0000 dB):
  - peak = 255 << (bitdepth − 8) = **1020** for 10-bit (HM/VTM/VVenC convention)
  - computed on 10-bit source vs 10-bit decoder output, frame i vs frame i (alignment check: best offset 0 in every run)
  - per component: arithmetic **mean of per-frame PSNR**
  - **YUV**: PSNR of the 4:1:1 pixel-count-weighted mean MSE (VVenC "YUV-PSNR")
  - also stored: peak 1023 / PSNR-of-mean-MSE (FFmpeg convention, cross-checked to 6 decimals in Phase 3) and (6Y+U+V)/8 (JVET CTC)

## 5. Pilot (36 runs, 2026-10-27 19:45–20:19, all exit 0, all on AC power)
Reduced frame counts: 64 frames (240p, 480p), 32 frames (1080p). Data: `results/pilot/results.csv`, `pilot_estimates.csv`, `pilot_summary.json`.

Checks:
| Check | Result |
|---|---|
| Repeatability (BasketballPass, 64 f, QP32 medium ×3) | bitstreams identical; encode wall 10.20 / 7.46 / 7.48 s (CV 18.8 %; first run was the outlier) |

## 7. Recommended matrix
**Option A (recommended):** all 32 configurations at full length + 2 extra timing repeats (encode + pure-decode only, no reconstruction written) for all 8 configurations of the two 240p sequences; one warm-up run; seeded random order (seed 2026). Estimated ≈ **8.6 h** (range ~7–11 h), recon ≈ 33.0 GB (80.8 GB free on D:). Already generated as `configs/full_manifest.json` (65 runs).

Alternatives: B — as A but BasketballDrive limited to its first 100 frames (≈5.8 h); C — A without timing repeats (≈6.2 h, timing reported from one run only).

## 8. Limitations
- Timing on a hybrid-core laptop (4 P + 8 E cores, Balanced plan) is noisy; single-run timings can be off by ~30 %. Repeats + medians mitigate this for the 240p sequences only.
- Preset comparison at a single QP changes both bitrate and PSNR at once; it is one rate-distortion point per preset, not a BD-rate comparison.
- All sources have 8-bit effective precision; results may differ for true 10-bit content.
- Windows-only measurements so far; Linux build pending.
